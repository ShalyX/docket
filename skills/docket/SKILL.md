# Docket GitHub Delivery Skill

Use this workflow when a public GitHub pull request is the delivery artifact for a Docket task. Its purpose is to give a worker agent compact, reproducible evidence for a task and give the requester a clear review path. The GitHub Action is evidence collection only; Docket's contract remains the authority for escrow and settlement.

## Preconditions

- The repository and pull request are public on `github.com`.
- A requester and worker have agreed the checklist, weights, escrow amount, and task ID.
- The checklist has two to five criteria and weights sum exactly to 10,000 basis points.
- The repo contains the exact canonical v2 public `docket.yml` generated by Docket, with a canonical lowercase `repository_url`, non-zero lowercase `worker_address`, positive `escrow_wei`, and a `task_id` beginning with `dkt-`, 12–64 characters long, using lowercase letters, digits, and single hyphens. Keep the file at the repository root and at or below 64 KiB.
- No configuration or evidence field contains a private URL, token, credential, private log, or customer data.

## Configure and register the task

1. In Docket, enter the worker, repository, title, escrow, and criteria, then choose **Prepare docket.yml**. Copy or download the exact generated file and acknowledge in the browser that it will be committed unchanged at the target repository root before a delivery PR opens. Docket persists the prepared bytes and hash locally so a reload does not erase the handoff. The acknowledgement does not prove a GitHub commit.
2. Have the requester call `register_task(task_id, worker, repository_url, title, checklist_json, config_sha256)` with the agreed GEN value. `config_sha256` must be the generated file’s normalized lowercase SHA-256; the contract reconstructs and verifies the exact v2 file from the terms and checks the repository is active and public before it locks funds.
3. Vendor [the Docket Action directory](../../integrations/github-action) into the target repository at `.docket/github-action`, then add [target-repo-workflow.yml](../../integrations/github-action/target-repo-workflow.yml) as `.github/workflows/docket-evidence.yml`. The template checks out `github.event.pull_request.head.sha` with `persist-credentials: false` and publishes the two Action outputs in the job summary. A published Action may replace this local path only at an immutable tag or commit SHA.
4. Record the returned task ID and configuration hash. The task checklist and `config_sha256` in the contract, not a later edit to the repository config, are the frozen agreement.

## Submit delivery evidence

1. The worker opens or updates the public PR. The `pull_request` workflow runs the Docket evidence action.
2. Open the successful workflow run's job summary and copy both the `manifest` and `proof` JSON objects. Before submitting them, verify all of these facts:
   - `proof.schema_version` equals `docket.github-evidence-proof.v1`, and `proof.task_id` equals the on-chain task ID.
   - `proof.repository_url` equals the onchain repository and `proof.config.sha256` equals `get_task(task_id).config_sha256`.
   - `proof.manifest_sha256` equals `manifest-sha256`.
   - `proof.workflow_run.id` equals the run-ID segment in `manifest.actions_run_url`, and `proof.workflow_run.attempt` is positive.
   - `manifest.head_sha` is the commit being offered as delivery, and `manifest.pr_url` and `manifest.actions_run_url` are canonical public `https://github.com` URLs for the intended repository.
3. Paste both outputs into Docket. The browser requires both and verifies the proof locally, then submits the exact `manifest` output as the worker's `submit_delivery(task_id, evidence_manifest_json)` input. It must remain a flat JSON object with only `pr_url`, `head_sha`, and `actions_run_url`; do not submit the separate `proof` object or add private context.
4. The requester calls `get_task(task_id)` to review the status and evidence. A requester may accept delivery for the full payout, or call `open_dispute(task_id, reason)` when a criterion is not satisfied.

## Dispute and status handling

| Situation | Contract action |
|---|---|
| Work meets the agreed checklist | Requester calls `accept_delivery`. |
| A criterion appears incomplete | Requester calls `open_dispute`, then either party calls `resolve_dispute`. |
| Requester does not review a submitted task | Worker may call `escalate_submission(task_id, reason)` after the 24-hour review window. |
| Delivery head is superseded or validator evidence is inconclusive | Worker calls `supplement_evidence(task_id, evidence_manifest_json)` with an updated public manifest while the case is submitted, disputed, or inconclusive; there are at most three evidence versions. |
| Adjudication returns `NEEDS_EVIDENCE` | Requester may call `refund_inconclusive_task` after seven days, or once the absolute 30-day deadline from case creation has elapsed. An amended or merely disputed case must be adjudicated into `NEEDS_EVIDENCE` first. |

`resolve_dispute` evaluates evidence against the frozen checklist; it does not automatically trust a passing GitHub workflow or offchain proof. It independently fetches root `docket.yml` from the public PR head repository at the submitted manifest head, normalizes line endings plus one final newline, and requires its hash and canonical v2 terms to equal registration. The head repository may be a public fork, while the PR base repository and Actions run still must match the task repository; the run must be a successful `pull_request` run linked to the submitted PR. A missing, oversized, unreadable, or mismatched file or workflow yields `NEEDS_EVIDENCE` rather than a disputed payout. Its deterministic disputed payout equals the sum of passed criterion weights, with the remainder returned to the requester. `accept_delivery` remains a requester-authorized full payout and does not run this GitHub check.

## Agent guardrails

- Never create an issue comment, merge a PR, publish a release, or submit a Docket transaction merely because an Action output exists. Those are separate, authorized actions.
- Never treat a URL, CI status, or PR title as proof by itself. Explain which checklist criterion each item supports.
- Do not fetch private repositories or forward credentials. The action deliberately rejects private-repository event payloads and does not read `GITHUB_TOKEN`.
- Preserve the exact manifest and its SHA-256 when handing evidence to another agent or reviewer. If the PR head changes, generate and review a new manifest.
